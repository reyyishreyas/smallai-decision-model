# SmallAI Decision Model: PRD and Tech Plan

*Product requirements and build plan for a lightweight, non-LLM, interpretable decision model with multi-step reasoning. Written for a Python-only builder.*

## 1. Summary

Build a small decision model from scratch (NumPy, no scikit-learn or xgboost for the core algorithm) that does not jump straight from input to answer. It evaluates intermediate steps first, checks them, and then makes a final decision. It is trained on both correct and deliberately wrong decision paths ("journey learning"), and it is benchmarked against a shortcut model, a rule-based heuristic and an LLM cost proxy for accuracy, latency and compute cost.

**Core idea in one line:** a tiny "chain-of-thought for tabular data" where each step is a predicted, checkable state, and a built-in verifier learns to tell good steps from bad ones.

## 2. Goals and non-goals

**Goals**

- Model under 100K parameters (target: under 10K), runs on CPU, under 10 ms per decision (realistically well under 1 ms).
- Every decision comes with a visible chain of intermediate states and a validity score for each step.
- Training explicitly uses incorrect trajectories and measurably improves robustness over a shortcut baseline.
- Fully reproducible: one command trains, one command evaluates, fixed seeds.

**Non-goals**

- No LLM or transformer training, fine-tuning or distillation.
- No external LLM API calls in the inference path.
- No GPU or large-scale infrastructure.

## 4. Problem definition (Task 1)

### 4.1 Environment: UAV pre-flight Go/No-Go

A drone mission planner decides whether a mission can proceed, based on sensor and mission readings.

**Input state (about 10 to 12 numeric features):** battery percent, wind speed, temperature, GPS fix quality, link signal strength, payload weight, distance to target, sensor health score, time of day, terrain difficulty.

**Reasoning steps (each outputs a discrete state):**

1. **Energy feasibility:** is required energy (distance, payload, wind) within battery? States: SURPLUS, MARGINAL, SHORTFALL.
2. **Environmental risk:** wind and temperature combined. States: LOW, MEDIUM, HIGH.
3. **Navigation and comms reliability:** GPS plus link plus sensor health. States: RELIABLE, DEGRADED, UNRELIABLE.
4. **Final decision:** GO, GO\_REDUCED\_PAYLOAD, HOLD, ABORT.

The oracle is a deterministic Python function that computes steps 1 to 3 from the features using explicit formulas and thresholds, then maps the step states to the final action using a rule table. Because the oracle is deterministic, every trajectory has a known correct answer.

**Why this environment:** it is structured and tabular, it has real intermediate states, and the final decision genuinely depends on them. If you want a different domain, keep the same pattern: features, then 2 to 4 intermediate states, then a final action, with a deterministic oracle.

### 4.2 Trajectory format

Each training example is a trajectory:

```
{features, step1_state, step2_state, step3_state, final_action, is_valid, first_bad_step}
```

- **Valid trajectory:** all steps match the oracle.
- **Invalid trajectory:** one or more steps are corrupted (wrong state, or a state that is illegal given the previous steps), and the final action may be wrong or inconsistent. `first_bad_step` records where it went wrong.

### 4.3 Data generation plan

| Set | Content | Purpose |
| --- | --- | --- |
| Train | About 50K feature vectors, each with 1 valid and 1 to 2 corrupted trajectories | Journey learning |
| Validation (in-distribution) | About 5K, same distribution | Tuning and early stopping |
| Test A: clean | About 5K | Basic accuracy |
| Test B: noisy | Sensor noise added to features | Robustness |
| Test C: shifted | Feature ranges moved (for example more wind, lower battery) | Generalisation, where journey learning should help most |

Generate the corrupted paths with several strategies: random step flip, "plausible mistake" (neighbouring class), and shortcut mistake (final action that ignores the steps).

## 5. Model design (Task 2)

### 5.1 Architecture

- **Encoder:** features go through Dense(32, ReLU) then Dense(32, ReLU) to give an embedding `h`.
- **Step heads (sequential):** step k takes `[h, one-hot of previous steps]` and applies Dense then softmax over that step's states. Because step 2 sees step 1's output, the chain is genuinely sequential.
- **Final head:** takes `[h, all step one-hots]` and applies Dense then softmax over actions.
- **Verifier head:** takes `[h, step k state one-hot, k]` and applies Dense then sigmoid, giving the probability that this step is valid. This is the self-verification part.

Estimated size: roughly 3K to 8K parameters.

### 5.2 Inference procedure

1. Encode features.
2. For each step: predict the state, run the verifier, record the validity score.
3. If any step's validity is below a threshold, flag the decision as low confidence (optionally fall back to the rule-based heuristic or output HOLD).
4. Output the final action plus the full trace.

Example output:

```
Energy: MARGINAL (valid 0.97) -> Environment: HIGH (valid 0.93) -> Nav: RELIABLE (valid 0.99) -> Decision: GO_REDUCED_PAYLOAD
```

### 5.3 Loss design

```
L = a * CE(final) + b * sum_k CE(step_k) + c * BCE(verifier) + d * L_format
```

- **CE(final):** the final decision is right.
- **CE(step\_k):** each intermediate step is right (only on valid trajectories).
- **BCE(verifier):** the verifier labels valid trajectories as 1 and corrupted ones as 0. This is where the incorrect paths are learned from.
- **L\_format:** penalises probability mass on illegal step combinations (the analogue of the article's format reward). Define a small legality table from the oracle.

Start with a = b = c = 1 and d = 0.2, then tune on validation.

### 5.4 Building it from scratch

- Write Dense layers with explicit forward and backward passes in NumPy.
- Implement ReLU, softmax with cross-entropy (use the log-sum-exp trick for stability), sigmoid with BCE, and Adam or SGD with momentum.
- **Verify with a numerical gradient check** (finite differences) in a unit test. This is your proof that the from-scratch implementation is correct, and it is the first thing a reviewer will want to see.

### 5.5 Optional stretch

A from-scratch decision tree (Gini splits plus rule extraction) as a second interpretable model and a stronger baseline. Only do this after everything else is done.

## 6. Baselines and evaluation (Task 4)

### 6.1 Models compared

| Model | Description |
| --- | --- |
| B0: Heuristic | Hand-written threshold rules, no learning |
| B1: Shortcut MLP | Same encoder, features directly to final action, no steps, trained on valid data only |
| B2: Steps, no journey learning | Full step architecture trained on valid trajectories only |
| **M: Full model** | Step architecture plus verifier, trained with journey learning |
| B3: LLM proxy (offline only) | Cost and latency estimate for solving the same task with an LLM. Do not use it in inference; compute it analytically from token counts and published pricing. |

The B1 and B2 comparison is the one that proves journey learning works.

### 6.2 Metrics

| Metric | How |
| --- | --- |
| Final accuracy and macro-F1 | On Test A, B and C |
| Step accuracy | Per intermediate step |
| Verifier quality | Precision, recall and AUC for detecting corrupted steps |
| Step-consistency rate | Share of outputs whose steps obey the legality table |
| Latency | p50 and p95 per decision over 10K runs with `time.perf_counter`, single thread, after warmup |
| Compute and memory | Parameter count, FLOPs per decision, peak memory via `tracemalloc` |

### 6.3 An honest warning about the results

On clean synthetic data produced by a deterministic oracle, a shortcut MLP may reach near-perfect accuracy, which would leave journey learning nothing to improve. That is why Test B (noise) and Test C (distribution shift) and the verifier metrics exist. If you only report Test A, the improvement criterion may fail for a reason that has nothing to do with your implementation. Plan the evaluation so the benefit can show up where it genuinely exists, and report negative results honestly if it does not.

## 11. Risks and mitigations

| Risk | Likelihood | Mitigation |
| --- | --- | --- |
| Backprop bugs | High | Gradient check test before any training; start with a tiny batch overfit test |
| Journey learning shows no gain on clean data | High | Use noisy and shifted test sets; report honestly |
| Oracle too easy, so every model hits 100% | Medium | Add feature interactions, overlapping thresholds and label noise |
| Verifier cheats by detecting corruption style | Medium | Use several corruption strategies, and hold out one strategy at test time |
| Scope creep (trees, Q-learning, demo) | Medium | Treat them as stretch goals after acceptance criteria are met |
| X% undefined | Certain | Agree the number with the lead before starting |
